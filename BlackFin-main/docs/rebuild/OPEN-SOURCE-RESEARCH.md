# Open-source research for the BlackFin replacement

Research date: 2026-09-12. Status: **evaluation and proposed selections, not installed or validated integrations**. This report responds to the request to replace the rejected application with an internal, investment-grade multifamily research and analytics platform. A high-quality map is central, with a linked dense analytical table. Free public data comes first. See the companion public-data research for actual source coverage.

## What this search established

There are reusable financial, geospatial, extraction and analytical engines. There is no verified, complete open-source product in this search that supplies Florida property/loan aggregation, reviewed multifamily underwriting, current operating comparables, lender/sponsor analysis, and calibrated investment grading out of the box. We should test substantive engines before writing another homegrown model, while building the domain contracts, lineage, comparisons and user experience those engines do not provide.

The earlier inventory of candidate links was not an integration. Installing an agent skill is not implementing its concepts; a passing unit test is not independent financial acceptance; a market-data adapter is not a multifamily loan feed. The replacement must demonstrate actual imported records and reproducible analysis before product-completion claims.

Method: primary project documentation, repository license text, GitHub public repository metadata, and limited source inspection. No downloaded code was installed or executed. Repository `pushed_at` dates below were read from the GitHub API on the research date; they indicate activity, not a release, maintainer support commitment, or quality. Financial correctness, dependency compatibility, deployment cost and performance remain untested unless explicitly stated otherwise. Before adoption, pin the selected release and record its immutable commit, dependency licenses and tests.

### Concrete source-level reason for the bakeoff

At commit [`83e8baa`](https://github.com/rubyh218/re-pe-acquisition/blob/83e8baa719427c2f3960dc2c000f6c2f5839c0b3/scripts/underwriting/pro_forma.py), the acquisition candidate uses a predefined concessions burnoff and a default stabilized-year choice. These are consequential model assumptions rather than universal multifamily facts. The source also creates annual cash-flow dates from closing month/day, which deserves leap-day and partial-period cases. This was a limited read, not a full audit or runtime defect finding. Any adoption must expose conventions, test timing, and preserve the user's scenario choices.

### Earlier methodology resources: useful, but distinct from OSS engines

- **Adventures in CRE:** pay-what-you-can workbooks are not an OSI-style open-source license. Current [download terms](https://www.adventuresincre.com/terms-conditions-use/) and [AI policy](https://www.adventuresincre.com/ai-usage-policy/) impose attribution/version-tab requirements and restrictions relevant to AI-generated or derived tools. Do not port formulas, import a bundle, or classify it as a freely reusable engine on the strength of a zero-dollar download. Obtain an applicable grant before such reuse. No model was downloaded in this research.
- **Fannie Mae Multifamily Income Analysis:** a product-specific underwriting methodology source, not a general open-source calculator. The [multifamily guide](https://mfguide.fanniemae.com/node/3041) discusses supported cash-flow inputs and historical operating evidence. Do not confuse this with Fannie Mae's single-family Income Calculator. The prior direct `node/7526` link returned 403 during this research.
- **NCHMA:** the [current standards page](https://www.housingonline.com/councils/national-council-housing-market-analysts/model-content-standards/) identifies September 2025 updates, versioned content and associated white papers. Use it to define market areas, comparable selection and study completeness. It is a methodology source, not a dataset or model that automatically certifies our outputs.
- **NCREIF/PREA:** [reporting standards](https://user.ncreif.org/reporting-standards/) support consistent reporting, but public methodology does not confer rights to a historical property-return database. The page restricts redistribution of NCREIF data without consent. Benchmark definition, coverage and use rights must be verified separately.

### What grading and comparisons actually require

The initial release can provide useful, transparent screening without pretending to predict success. Proposed outputs are separate columns: observed facts; scenario calculations; policy thresholds; empirical percentile/comparison; freshness/completeness; and why a record matched a query. A hidden weighted score combining all six is unacceptable.

For each comparison metric, define numerator, denominator, units, reporting period, treatment of concessions/reserves/capex, geographic market, asset class/unit mix, affordability restrictions, vintage, sample size and exclusions. Show the cohort records and distribution behind a percentile. A HUD program subset cannot be silently presented as all Florida multifamily. NCREIF unlevered property returns cannot be treated as net levered LP IRRs. Appraisal/assessment values are not executable purchase prices.

A proposed outcome model needs dated observed outcomes, negatives and failed deals, not just published successful projects. Preserve the data available at the decision date. Use temporal/geographic holdouts and measure retrieval precision/recall, precision at the user's review capacity, reliability/calibration and stability across markets. The [scikit-learn calibration guide](https://scikit-learn.org/1.7/modules/calibration.html) also explains why Brier/log loss reflect more than calibration alone; use reliability plots and outcome-specific analysis rather than one flattering accuracy number. Until sufficient outcomes exist, label policy flags as policy flags and uncertainty as uncertainty.

### Basemap, aerial, style and font choices

**Proposed free-data starting point:** use a versioned Florida Protomaps vector basemap extract, restrained custom style, and a separate dated public aerial layer. [Protomaps download documentation](https://docs.protomaps.com/basemaps/downloads) supports regional extracts and warns against hotlinking its download URLs. The basemap is derived from OpenStreetMap and requires appropriate attribution; its [code license](https://github.com/protomaps/basemaps/blob/main/LICENSE.md) and [data attribution requirements](https://github.com/protomaps/basemaps/blob/main/LICENSE_DATA.md) are distinct. Avoid downloading a planet file when a Florida extract meets scope. Storage, range requests, tile generation and egress still cost money even when the data and libraries have no license fee.

Public `tile.openstreetmap.org` is not an unlimited production CDN; its [tile policy](https://operations.osmfoundation.org/policies/tiles/) prohibits bulk/offline tile harvesting and offers best-effort availability. Do not build an archive by scraping it. An OSM-based basemap is location context, not parcel ownership evidence.

The data research verified the official [USGS NAIP ImageServer](https://imagery.nationalmap.gov/arcgis/rest/services/USGSNAIPImagery/ImageServer), with acquisition-year/state/download fields and primarily 0.6 m imagery, and Florida FDOT APLUS as a higher-resolution county/year archive candidate. Treat aerials as dated photography: show acquisition year, resolution and source; unknown construction after capture stays unknown. A public ImageServer is not proof of durable low-latency hosting or a service guarantee. The source report covers bulk-download access and Florida imagery details. Do not substitute unreviewed commercial imagery/NAIP Plus gap fillers.

Before choosing a style bundle, inventory its JSON, sprites, icons and every font/glyph license. Use an owned style and redistributable fonts with notices recorded; no hard-coded third-party glyph endpoint is required. Check requested zoom coverage, retina rendering, CORS/range behavior, outage fallback and attribution placement in the actual browser. No final style/font bundle, imagery-hosting design, Railway cost, or new service has been selected or provisioned.

### Map acceptance contract proposed for the replacement

1. At property zoom, crisp parcel edges and selected-property geometry remain visible over both vector and aerial layers. Parcel source/county/vintage and address-location precision are inspectable. A point is not silently promoted to a verified parcel.
2. Map, grid and inspector use the same canonical property IDs, query definition, as-of date and result set. A polygon filter changes all three; clicking a row highlights its feature; clicking a feature selects its row. Overlapping parcels and multiple loans/property must be navigable.
3. Server-computed counts/cohorts include the complete matching dataset, not just the rendered tiles or loaded grid page. Clusters are labeled as aggregation and expand honestly. Boundary holes, multipart parcels, wrong CRS and invalid geometry have explicit cases.
4. Display simplification cannot change exact spatial eligibility results. Intersecting a program/flood/zoning layer gives a sourced spatial observation, not legal eligibility or an engineered determination.
5. First-map load, pan/zoom responsiveness, tile latency, memory, grid filter latency and keyboard usability are measured on real Florida layers at statewide, metro and parcel scales. Suggested initial targets for planning: useful map within 3 seconds on the agreed test connection, typical pan at 30+ fps, and p95 linked-filter response below 1 second on the agreed representative dataset. These are proposed targets, not current results; record hardware, counts, cache state and data vintage.
6. Query/selection state survives a reload; source failures stay visible. Authenticated tile/data endpoints reject unauthenticated access, and private attributes cannot leak into public basemap archives, error messages or shared caches.

## Minimal proposed combination and reuse-vs-build decision

**Start with:** PostgreSQL/PostGIS; MapLibre; one community dense-grid component; Terra Draw when spatial selection ships; a versioned static basemap; one staged-data engine (DuckDB is the initial finalist). Build source adapters, observations/identities, query contracts, provenance and linked map/grid interactions around a real public-data slice. Existing auth or deployment code is salvageable only after the replacement review; it does not dictate the product design.

**Financial selection remains a bakeoff:** Rangekeeper versus selected MIT-licensed acquisition/asset-management modules versus a deliberately small custom engine, all on the same independently reviewed cases. PyXIRR is a likely return primitive, not an excuse to skip the cash-flow engine. A Python worker/API is a justified option because substantive candidates live in Python; keep Node 24 for the existing web boundary if it survives review. Test Python 3.12 compatibility initially for Rangekeeper, rather than forcing it into Node or assuming Python 3.13 works. Do not deploy a new service until the winning integration and costs are concrete.

**Defer:** QuantLib until debt instruments require it; AbsBox until loan-pool strategies require it; Docling until source documents require OCR; Splink until exact matching leaves meaningful residuals; deck.gl/Martin until performance or integration evidence justifies them; ML/grading packages until outcome data supports evaluation. This is a sequencing proposal, not a rejection of the broader analytical scope.

## Open questions that research cannot resolve alone

The detailed investment policy and lender/product conventions; independent reference-case reviewer and permitted workbooks; coverage/rights for later operating statements and loan terms; representative historical outcomes; exact all-Florida source volumes; map hosting cost and acceptable response-time hardware; extraction accuracy on the actual document mix; and final engine/version selection. None prevents building the first honest, sourced public-data discovery slice. None is solved merely by adding tools from this list.
