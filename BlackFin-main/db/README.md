# Private workspace database

Use PostgreSQL 16 or newer. The data access layer requires `DATABASE_URL` and performs no DDL during requests. The production entry point does not run migrations. Operators run `node scripts/db-migrate.mjs` explicitly before deploying a release that requires a new schema. For local development using `.env.local`, run `node --env-file=.env.local scripts/db-migrate.mjs` from the application root before starting a newly configured workspace; standalone Node scripts do not automatically load that file. Migration filenames are applied in order with transactions, an advisory lock and recorded SHA-256 checksums. Re-running skips unchanged applied migrations. Correct deployed schemas using a new migration; do not change an applied file or reset tables.

`DATABASE_SSL_MODE=verify-full` is the default for remote connections and verifies the certificate. `DATABASE_SSL_CA` optionally supplies a private CA. `sslmode=require` also uses certificate verification in the application. Plaintext is permitted only for loopback or explicitly configured Railway private-network hosts using `DATABASE_SSL_MODE=disable`. Do not expose a PostgreSQL port without network/access controls. These settings do not choose or provision a database service.

Migration `005-research.sql` adds immutable source observations, source snapshots, research properties, tract geometry, import history and saved financing analyses; see the [research release contract](../docs/RESEARCH-RELEASE.md). Private import is an explicit operator CLI action, not an HTTP upload or startup task.

Migration `006-strategy-cases.sql` adds `research_strategy_cases` (one immutable origin per case: snapshot, property record, selected instrument, research filters, scenario and threshold at capture) and `research_strategy_case_versions` (append-only state, lane, content including the evidence register, reason and actor per save). Both tables reject UPDATE and DELETE through the existing history trigger. The migration also widens the `workspace_audit` event check constraint with `case.created` and `case.versioned`, which takes a brief exclusive lock on that table; the previous application never writes those events, so rolling the application back is compatible while the widened constraint stays in place. Case writes use the same `workspace_requests` idempotency keys as manual deals; see [strategy cases](../docs/RESEARCH-RELEASE.md#strategy-cases). `node scripts/research-db-test.mjs` exercises the case tables on an isolated database.

Migration `007-oz-eb5.sql` adds the read-only OZ / EB-5 designated tract table: `research_oz_eb5_runs` (one imported screen run, content addressed by the SHA-256 of its import manifest, with the source receipts, counts and the rule it applied), `research_oz_eb5_tracts` (one row per designated 2010 census tract, every column of the offline `oz-eb5-tracts.csv` preserved verbatim plus a simplified HUD display polygon that is NULL for metropolitan tracts), `research_oz_eb5_cbsa_counties` (OMB Bulletin 23-01 List 1 by county, Connecticut on planning regions, carried with the run so the server-side site test can answer the metropolitan leg for any county rather than only the counties holding a designated tract) and `research_oz_eb5_current` (the one live run pointer). All three history tables reject UPDATE and DELETE through the existing `workspace_reject_history_change` trigger; the pointer table deliberately does not, because switching it is how a newly imported run goes live. The migration is additive and creates no foreign key into the existing research snapshot tables, so the two imports are independent. Loading is an explicit two-step operator CLI action — `node scripts/prepare-oz-eb5-import.mjs` offline, then `node scripts/import-oz-eb5.mjs <bundle>` — never an HTTP upload, a startup task or a scheduled job; re-importing the same bundle replays and re-points the current run instead of duplicating rows, and a failure rolls the transaction back and leaves the previously imported run live. Apply 007 explicitly before releasing the application code that reads it; see the [release contract](../docs/RESEARCH-RELEASE.md#oz--eb-5-tracts). `node scripts/research-db-test.mjs` exercises these tables on an isolated database.

Migration `008-oz-eb5-extensions.sql` extends that table and adds the asset layer. It adds twenty-six nullable columns to `research_oz_eb5_tracts`, the ones the offline screen appended after `notes`: the 2027 nomination round (`oz2027_*`), the LIHTC Qualified Census Tract and Difficult Development Area flags and the NMTC low-income-community reading (`lihtc_qct_2026*`, `lihtc_dda_2026*`, `nmtc_*`), and ACS demographics at designation and latest (`acs2015_*`, `acs2024_*`); each verdict column carries a CHECK on its documented words and each measured column a range CHECK, and a NULL means the run's bundle did not carry the value, never an invented one. It creates `research_oz_eb5_assets`: one row per subsidized property from the screen's `assets` mode (HUD-assisted multifamily, USDA rural housing, LIHTC allocation records), keyed by run, source and source object id, with a foreign key to the tract row of the same run so an asset can only name a designated tract the run holds; every column of the offline `oz-eb5-assets.csv` is preserved and no owner, agent, phone or email field exists. The assets table rejects UPDATE and DELETE through the same history trigger. The import parser is now `oz-eb5-import-2`: a bundle from the earlier parser is refused whole rather than loaded without its assets, and an asset whose class disagrees with its tract is refused before a row is written. Apply 007 and 008 together, explicitly, before releasing the code that reads them; startup performs no schema change.

The supporting manual-workspace schema has one fixed workspace, a foreign-key constrained 67-county Census catalogue, manual deal records, append-only evidence metadata, immutable numeric/research decision snapshots, a draft mandate, actor audit records, and idempotency records. Application reads and writes each require an authenticated, allowed workspace session. SQL parameters and the fixed workspace scope are applied in the DAL. The same named users share the deal records. Each user row is either an email identity with no GitHub columns or a GitHub identity with all three GitHub columns; `db/004-email-identities.sql` enforces that shape. The database credential is a trusted server/operator credential and must remain private; this is not a claim that a leaked superuser connection is protected by application authorization.

New records may be research or screening. Diligence/closed stages require a preserved advance screening; passed requires a preserved reasoned pass. Qualitative research/pass snapshots may have unknown finances and contain no financial calculation. Numerical snapshots run the deterministic annual finance module on the server and retain its warnings. Advance means the user's next research step, not investment-policy or lender approval. Mandate saves always remain draft. Both workflows retain the then-current deal, evidence contents, source/effective/retrieval dates, model result/version, actor and reason. Evidence corrections are added as new dated records; original evidence and decision content cannot be updated or deleted through the application or ordinary SQL writes.

Each mutation requires a client-generated UUID `requestId`. Successful identical retries return the saved result without repeating a write; failed transactions do not consume the key. Changed payloads cannot reuse a successful key. Deal and mandate edits also require the previously read `expectedUpdatedAt`; a locked comparison rejects stale edits, and each successful update advances the timestamp by at least a millisecond. An unconfigured mandate sends an explicit empty version, meaning `null`; only one of two concurrent first saves can succeed. A conflict preserves the saved draft and does not consume the unsuccessful submission's idempotency key.

## Local checks

`node --test tests/workspace/*.test.ts` runs pure validation/financial-boundary tests; the integration test is explicitly skipped without its dedicated database variable. With a loopback database named `radar_test` in `DATABASE_URL`, run `node scripts/db-test.mjs`. This creates a new `radar_test_workspace_*` database, migrates it, and runs actual SQL/service tests using a mocked identity boundary. Tests exercise authenticated/denied service entrypoints, concurrent retry idempotency, source ownership, transaction rollback, safe cents, immutable records, qualitative decline with unknown finances, stale edits and draft policy. The identity mock does not verify real OAuth/MFA/session behavior; the separate auth checks must establish that boundary. No production database is accepted by the integration runner. Test databases remain available for inspection.

## Backup and isolated restore check

With writes paused, `node scripts/db-backup.mjs` creates an ignored local `.local/backups/*.dump` archive and a checksum/table-content manifest. Install matching PostgreSQL command-line tools; `PG_BIN` may name their binary directory. If a custom CA is required, also set `PGSSLROOTCERT` to its file for `pg_dump`/`pg_restore`. The local archive is private and unencrypted by this script; protect its storage separately. Keep archives out of Git, public assets and app/web filesystem upload flows.

Create a separate **empty loopback** PostgreSQL database beginning `radar_restore_` or `radar_test_`. Set `RESTORE_DATABASE_URL` to that target and `BACKUP_FILE` to the explicit archive. `node scripts/db-restore-check.mjs` verifies its checksum, refuses nonempty/nonlocal targets, restores without `--clean`, and compares every public table's row count and logical content hash. Fingerprints use a dedicated PostgreSQL session with its time zone set to UTC, and order both tables and row JSON using explicit `C` collation. This removes session-time-zone and default-collation differences from the comparison; it is not a guarantee of identical serialization across all PostgreSQL major versions or extensions. It writes a local evidence report beside the archive. A failed attempt leaves only its isolated target to inspect; it never overwrites an existing set of tables.

The app continues to report recovery `not_verified`. A successful local synthetic database exercise establishes that procedure only. Production backup retention, protected archive storage, recovery ownership/RPO/RTO, production restore and private document restore still need actual verification. Private-document upload and document import remain unavailable. The source-to-analysis release separately supports operator-run research snapshot import; that capability does not enable document storage or establish ongoing recovery readiness. The [release contract](../docs/RESEARCH-RELEASE.md#verification-and-recovery) records the narrower production archive/restore exercise.
